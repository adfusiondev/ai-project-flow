The MVP defines the smallest useful first version of the project.

## What this stage is

MVP planning decides exactly what the first version must include to be valuable, and — just as importantly — what it will deliberately exclude.

## Why it matters

Without an explicit MVP, projects tend to grow during implementation and never reach a useful, testable state. An explicit MVP keeps the first version small enough to finish and verify.

## What to define

- **MVP goal** — the outcome the first version must achieve.
- **MVP scope** — the features included.
- **Out of scope** — features intentionally excluded.
- **MVP success criteria** — measurable conditions for calling the MVP successful.

## Rules to follow

- Keep the MVP small, useful, and testable.
- Separate must-have features from future ideas.
- Do not add features only because they may be useful later.

## What should be completed before moving on

- `docs/MVP.md` exists.
- The core value is clear.
- The scope is limited.
- Future features are separated.
- Success criteria can be checked.

Move to **Requirements** when the MVP can be summarized in a few sentences and its success criteria are checkable.
